# План адаптации EDT-MCP под EDT Ruby 2024.2.5

## Цель

Получить собираемый и работоспособный вариант плагина для `EDT Ruby 2024.2.5` с минимально необходимым функционалом:

- запуск сервера;
- базовые project/code tools;
- рабочие `get_applications`, `update_database`, `debug_launch`.

## Исходные факты

- Текущий `master` уже переведен на `EDT 2026.1`.
- Для `EDT 2024.2` отсутствует IU `com._1c.g5.v8.dt.platform.support_v8.5.1.feature.feature.group`, который сейчас прописан в target.
- В `EDT 2024.2` есть `IApplicationManager`, но нет нового update API, на котором сейчас завязаны инструменты:
  - нет `ApplicationUpdateState`;
  - нет `ApplicationUpdateType`;
  - нет `IApplication.getRequiredVersion()`;
  - нет методов `getUpdateState(...)` и `update(...)` в нужной форме.
- В `EDT 2024.2` есть старый совместимый слой для работы с инфобазами:
  - `com.e1c.g5.dt.applications.infobases.IInfobaseApplication`;
  - `com._1c.g5.v8.dt.platform.services.core.infobases.sync.IInfobaseSynchronizationManager`.
- `ServiceAccess` в `2024.2` есть, то есть это не блокер первого этапа.
- Отдельного публичного p2 endpoint именно для `2024.2.5` нет; ориентируемся на официальную ветку `2024.2`.

## Рекомендуемая база

Основной вариант:

- портировать не от текущего `master`, а от состояния до миграции на `2026.1`;
- отправная точка: коммит `a91f773` или релизная линия уровня `1.26.1`.

Запасной вариант:

- если нужно портировать именно текущий `master`, сначала откатить target/dependency drift, потом переносить application/update слой.

## Этапы

### 1. Зафиксировать ветку для порта

- создать отдельную ветку, например `port/edt-2024.2.5`;
- выбрать базу: `a91f773` предпочтительнее, чем текущий `master`;
- сохранить текущие проверки и выводы в commit message или отдельной заметке.

### 2. Подготовить target platform под 2024.2

- заменить URL target-платформы на `https://edt.1c.ru/downloads/releases/ruby/2024.2/`;
- удалить из target `com._1c.g5.v8.dt.platform.support_v8.5.1.feature.feature.group`;
- прогнать `mvn -f mcp/pom.xml -DskipTests package` и собрать список следующих блокеров;
- не трогать лишние IU, пока не появится реальная ошибка resolve.

### 3. Согласовать OSGi зависимости

- проверить `Import-Package` в `mcp/bundles/com.ditrix.edt.mcp.server/META-INF/MANIFEST.MF`;
- ослабить или убрать диапазоны версий, которые не покрываются `EDT 2024.2`;
- отдельно проверить пакеты из слоев:
  - `dt.core.lifecycle`;
  - `dt.core.platform`;
  - `dt.metadata.common`;
  - `dt.metadata.mdclass`;
  - `dt.metadata.mdclass.util`;
  - `dt.check.settings`;
  - `com.google.common.base`.

### 4. Переписать application/update слой на старый infobase sync API

#### `get_applications`

- файл: `mcp/bundles/com.ditrix.edt.mcp.server/src/com/ditrix/edt/mcp/server/tools/impl/GetApplicationsTool.java`;
- убрать использование `ApplicationUpdateState`;
- убрать вызов `app.getRequiredVersion()`;
- если приложение реализует `IInfobaseApplication`, заполнять статус через:
  - `IInfobaseSynchronizationManager.getSynchronizationState(...)`;
  - `IInfobaseSynchronizationManager.getEqualityState(...)`;
- вернуть совместимое человекочитаемое поле состояния, даже если его название придется поменять.

#### `update_database`

- файл: `mcp/bundles/com.ditrix.edt.mcp.server/src/com/ditrix/edt/mcp/server/tools/impl/UpdateDatabaseTool.java`;
- убрать `ApplicationUpdateState` и `ApplicationUpdateType`;
- перейти на `IInfobaseApplication.getInfobase()`;
- обновление выполнять через `IInfobaseSynchronizationManager.updateInfobase(...)`;
- отдельно принять решение по `fullUpdate`:
  - либо временно деградировать в обычный update;
  - либо маппить на `reloadInfobase(...)`, если это подходит по поведению;
  - либо явно вернуть ограничение в результате инструмента.

#### `debug_launch`

- файл: `mcp/bundles/com.ditrix.edt.mcp.server/src/com/ditrix/edt/mcp/server/tools/impl/DebugLaunchTool.java`;
- убрать pre-launch update через `appManager.update(...)`;
- перед запуском проверять sync/equality state;
- если база требует обновления, вызывать `updateInfobase(...)`;
- запуск launch configuration оставить как есть, если internal IDs в `2024.2.5` не изменились.

### 5. Сборка до зеленого состояния

- после каждого блока изменений прогонять:
  - `mvn -f mcp/pom.xml -DskipTests package`;
- фиксировать compile errors пакетами, а не по одному классу;
- как только Java-компиляция пройдет, проверить сборку feature/repository.

### 6. Ручная проверка в реальном EDT 2024.2.5

- установить собранный плагин в локальный `EDT 2024.2.5`;
- проверить:
  - старт плагина;
  - открытие workspace;
  - `get_projects`;
  - `get_applications`;
  - `update_database`;
  - `debug_launch`;
- отдельно проверить сценарий с реально подключенной инфобазой.

### 7. Доводка документации

- обновить `README.md`:
  - поддерживаемую версию EDT;
  - ограничения порта;
  - особенности `fullUpdate`, если останутся;
- при необходимости завести отдельную release note для линии `2024.2`.

## Критерии готовности

- target platform полностью резолвится на `EDT 2024.2`;
- `mvn -f mcp/pom.xml -DskipTests package` проходит без ошибок;
- в коде не осталось зависимостей от:
  - `ApplicationUpdateState`;
  - `ApplicationUpdateType`;
  - `IApplication.getRequiredVersion()`;
  - `IApplicationManager.getUpdateState(...)`;
  - `IApplicationManager.update(...)`;
- `get_applications`, `update_database`, `debug_launch` работают в `EDT 2024.2.5`;
- README не вводит в заблуждение по поддерживаемой версии.

## Риски

- `2024.2.5` не публикуется как отдельная p2 линия, поэтому часть выводов делается по `2024.2`.
- Семантика `fullUpdate` может не совпасть один в один с поведением ветки `2026.1`.
- `LaunchConfigUtils` использует внутренние ID/атрибуты launch configuration, которые нужно проверить живьем на `2024.2.5`.
- Если всплывут дополнительные несовместимости по пакетам `md`/`platform`, объем работ вырастет.

## Быстрый план работ

1. Создать ветку от `a91f773`.
2. Почистить target под `2024.2`.
3. Довести `MANIFEST.MF` до resolve.
4. Переписать три инструмента на `IInfobaseSynchronizationManager`.
5. Добить сборку.
6. Проверить в живом `EDT 2024.2.5`.
7. Обновить README и выпустить отдельную линию сборки.
